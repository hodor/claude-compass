# PLAN-025 detail

Reasons and long text for [[PLAN-025-review-across-files-and-sessions]]. Numbers like 1.13 are findings, H1 to H14 hypotheses and G1 to G22 open checks of [[research/human-surface/RESEARCH-review-across-files-and-sessions]]. Task lines appear without their checkbox so that no tool reads this file as a task list; the plan holds the live task lines.

## Choices, with reasons

- **Several files:** one review, one card, one answer. Today several files go out as several requests and are answered separately (4.4); GitHub, Gerrit and Phabricator close a review with one answer (1.13).
- **Marks per file:** read or not, plus an optional note; no approve per file. Every review tool surveyed keeps a yes-or-no mark per file beside one answer for the whole review, and none approves each file (1.16). Approving once also keeps decision D-04 of the spec: the human approves one time. The mockup of [[research/human-surface/RESEARCH-plugin-ui-mockup]] drew an approve per file (1.8, 1.9); the new mockup (TASK-210) shows the one-answer form.
- **When a file counts as read:** on opening, as Gerrit does with its preference on (1.12); a click per file would add clicks the walk is meant to save.
- **Moving between files:** the controls of the earlier mockup (1.8) and GitHub's single file mode (1.11). Opening a listed file, by a link or by hand, moves the walk to it (H4), so following a link never loses the place.
- **Where the walk lives:** the side panel stays while the human moves between files, and a block drawn in a document goes when he leaves it (5.2). The earlier mockup drew the walk as a block only because it had no panel (5.4). PLAN-024's TASK-206 therefore points to this plan for the walk (TASK-212).
- **Telling sessions apart:** two sessions in one vault give two cards with nothing telling them apart (2.9). The request gains `project` (the folder holding the vault) and `session` (the Claude Code session's id, read from `CLAUDE_CODE_SESSION_ID`, set by Claude Code in each session's environment); the mockup decides how the card shows them (H5).
- **Reviews of other projects:** each Obsidian reads only its own vault's reviews, and a wrong window refuses a file that is not its own (2.6). D-06 asks for several Obsidians, each guiding through its own files; a list across projects is an extra view, held by [[plans/PLAN-024-working-in-compass-is-visual]] TASK-206, which needs the names TASK-211 adds (5.8).
- **Which edits count:** an edit to a file no review names lands on the newest card, whichever session owns it (2.11), and the edited list picks up Obsidian's own table padding and files Compass writes (4.5, 4.6). Whether Obsidian's file-changed event fires for other programs' writes is open (G5); TASK-209 settles it before TASK-214 is detailed (H6). If the events cannot tell the human's typing from other writes, a review lists only edits to its own files.
- **Stepping aside:** the decision is made when the request goes out, by a check that finds any Obsidian window focused, another project's included (2.13, 4.8). The plugin knows whether its own window has focus, so each card decides alone (H6).
- **A link that reaches nothing:** the link opener ignores failure (2.15), and one forum report says a link to an already open vault does nothing (2.4), against Obsidian's docs (2.3). TASK-208 runs the check (G1 to G4); TASK-216 is built only if a link can fail (H7, H13).
- **Change report after an answer:** the diff printed after an answer covers the whole repository, so one session's report holds another session's work (2.12). What is lost: the waiting session no longer reads other files' changes inline; it sees their names, and `git diff <sha>` still shows them in full. Decision D-05 (know the deltas) holds for every file the review touched.
- **Approvals with several documents:** whether the skills that ask for approval can pass several files at once is unchecked (G18); the plan and its detail file, or a spec and its research, are the common pairs.
- **VS Code:** no finding shows the surface interface or the file exchange needing a change (3.1, 3.2, H8). Its blockers are window routing and raising (3.10, 3.12), so it follows the Obsidian walk instead of splitting effort. Cursor runs an older engine (3.17); VSCodium runs extensions that use only the public interface.
- **Two editors set up:** today the first configured surface wins and nothing lets a project prefer one (3.3, H9).
- **Stepping aside on VS Code:** no extension call raises or minimizes the window (3.12, medium confidence); `code -r` and `-g` bring a window forward at a file (3.15). Stepping aside is decision D-02 of the spec; on VS Code it holds only if TASK-220 finds a way (G12), otherwise VS Code stays in front after an answer (H12). Obsidian keeps it in full.

The document `RESEARCH-review-live-checks` is created with these results, one table per check.
- TASK-209: a throwaway plugin under `.compass/tmp/trials/review-edits/`, installed into this vault as `.obsidian/plugins/compass-review-edits/`, appends to `.compass/tmp/trials/review-edits/events.jsonl` each `vault.on("modify")` and `workspace.on("editor-change")` event with the path and time. A script lines the events up with the writes; the result goes into the live checks document, and the plugin is turned off.
- TASK-210: the mockup plugin `compass-ui-mockups` gains a side panel (an Obsidian item view on the right) holding two cards: the first walks four real files ([[specs/human-surface/SPEC-030-review-documents-open-in-obsidian]], this plan, its detail file and [[research/human-surface/RESEARCH-review-across-files-and-sessions]]) with a reason line per file, read marks set on opening, a note per file, and one Approve and one Needs changes; the second is a sample card from another session, labelled with its project and session. - TASK-211: request: `{"id", "surface", "file", "files": [{"file", "why"}], "session", "project", "title", "return", "commit"}`, `file` equal to `files[0].file` so the shipped plugin keeps working; `why` comes from an optional `--why "<path>=<line>"` flag, repeated. `session` is `CLAUDE_CODE_SESSION_ID` or empty, `project` the name of the folder holding the vault. The guard denies a subagent's write to any listed file of a pending review.
- TASK-212: TASK-206's line in [[plans/PLAN-024-working-in-compass-is-visual]] gains: the walk through several files is the panel of [[PLAN-025-review-across-files-and-sessions]], and its list of reviews across projects reads `project` and `session` from TASK-211. ## Wave 2 task text

- TASK-213: the card, top to bottom, as the mockup draws it. The panel opens with the heading "Reviews waiting on you" and lists one card per pending review, newest first. A card shows the question (the request's `title`, else the first file's name); a line with "Project" and the request's `project` (else the folder holding the vault) and "Session" and the first six characters of `session` (left out when `session` is empty); "File i of n" with Previous, Next and Next unread, and Left and Right arrow keys while the card has focus; one row per listed file with its read mark (read or unread), its title (the `title` property, else the file name), its `why` line and its note count, a click on the row opening that file; a note field labelled "Note on <title>" for the current file, keeping each file's note as the walk moves; the "On this file: <path>" box with its own note field while an open markdown file is not one the card lists; a line "x of n files read, N notes" (plus the notes on outside files); and one Approve and one Needs changes. Every move opens the file in the pane that already shows it, else the current pane, and marks it read; opening a listed file by hand or by a link moves that card's walk to it and marks it read. A one-file request (no `files`) draws the same card at "File 1 of 1". A newer request that lists any file of an older one replaces it, as Compass withdraws the older. Each listed file carries the one-line bar "Review: <question>, file i of n". The answer is `{"id", "file": first file, "verdict", "notes", "comments", "edited", "files": [{"file", "read", "note"?}], "at"}` in request order, `notes` holding the files' notes as `<name>: <note>` lines; a one-file answer keeps today's fields and its note as `notes`, with no `files`. Before writing the answer every listed file's editor is saved. Needs changes is enabled by a note on a listed file, a note on an outside file, or an edit. A rename keeps the file's mark, note and edit under its new path. `compass review --install` puts the build into this vault; the human reloads Obsidian once. The mockup plugin may stay on beside it for the comparison.
- TASK-214: the plugin listens to `workspace.on("editor-change", (editor, info) => ...)` and takes the file from `info.file`; edits come from this event alone, and a file-changed event marks none. An editor-changed event during a review adds the file to the `edited` set of every pending card listing it; an event on a file no card lists changes no card. After a card's answer its set is closed.
- TASK-215: `onRequest` reads `getCurrentWindow().isFocused()` before raising the window and stores it on the entry, also for a review the start-up scan already tracked. After an answer, once no review in this window is pending, Obsidian steps aside when any review answered since the window was last raised arrived without focus; a review that only the start-up scan saw uses the request's `return`. Compass keeps writing `return` from its own focus check, which also serves a plugin installed before this change.
- TASK-217: `changes_since` takes the paths to show in full: the request's files and the answer's `edited`, each turned from a path under the review surface's root into a path under the repository root. It prints `--- changes since <short sha> ---`, then `git diff <commit> -- <those paths>` under the same line cap, then `changed <path>` for each other path in `git diff --name-only <commit>`, then `untracked <path>` as before. `review.py` passes the paths after the answer arrives.
- TASK-218: the research gate of `/compass:research-codebase` becomes `compass review <research file> <spec file> --title "Follow-up questions, or move to planning?"` with a `--why` per file; the wave pause in step 7c of `/compass:build` sends the plan file with the documents the wave's tasks wrote results into, each with a `--why`. `plugin.json` goes to 0.30.0 and the Obsidian plugin's `manifest.json` to 0.2.0; `/compass:update` refreshes `.claude/` and `.compass/meta/plugin.yaml`, and `compass review --install` run in this repo and in the second project puts the new plugin into both vaults.
- TASK-219: the second project is `.compass/tmp/trials/second-project/` from TASK-208. Each three-file review is sent with `--why`; the one-file review comes from a second Claude Code session in this repo. In this vault the human opens a listed file in a second pane, opens a file outside the review and leaves a note on it, and renames one listed file before answering. Recorded per review: clicks, minutes from arrival to answer, how the human reached the window, and the answer's `files` and `edited` lists.

## Wave 3 task text

- TASK-220: a throwaway extension under `.compass/tmp/trials/vscode-probe/` registers a URI handler and, on each link, appends `{"at", "uri", "folder"}` to `.compass/tmp/trials/vscode-probe/events.jsonl`, `folder` being its window's first workspace folder; it also runs one command that tries every call `vscode.d.ts` offers near window state and records whether the window moved. It is installed with `code --install-extension` and `cursor --install-extension`. Cases, each sent from a script and timed: two windows open on this repo and on `.compass/tmp/trials/second-project/`, a link naming each folder in turn, sent while the other window is in front (G10, 3.10); `code -r <folder>` and `code <folder>` with the other window in front (G10, 3.15); the editor closed, then a `vscode://` link (G11); the same three cases in Cursor with `cursor` and `cursor://` (G14). Remote windows (G13) stay out: nothing in this repo runs under WSL. The results go into the live checks document, one table per case, with which window logged each link and which came forward.
- TASK-221: a throwaway extension under `.compass/tmp/mockups/vscode/` contributes a webview view to the Activity Bar holding the card of `plugin/obsidian/compass-review/main.js` as HTML, with the same parts as the Obsidian panel: the heading "Reviews waiting on you", the question, Project and Session, "File i of n" with Previous, Next and Next unread, one row per file with its read mark, `why` line and note count, a note field per file, "On this file" for an open file outside the review, and one Approve and one Needs changes. ## Wave 4 task text

- TASK-222: `reviewlib.choose` reads `review_editor` from `.compass/meta/plugin.yaml`; when set, that surface is tried first and the rest follow in the usual order, so a setting naming an editor that is not set up falls back to the first one found. `compass doctor` adds one line naming the editor reviews go to, a warning when the setting names an editor that is not set up, and an error for a name no surface has. The line `compass review --install` prints for a VS Code family editor says the extension is installed once for the user, not per project.
- TASK-223: `review_surfaces/vscode.py` has the seven parts every surface has (finding 3.1 of [[research/human-surface/RESEARCH-review-across-files-and-sessions]]; listed in `plugin/cli/review_surfaces/__init__.py`, where the new surface is registered after Obsidian), with `NAME = "vscode"` and a `cursor` variant differing only in its command. `configuration` finds the folder holding the vault and the editor's command on the path; `deliver` runs `<command> <folder>`; `has_focus` checks the foreground window's process (`Code.exe`, `Cursor.exe`) as the Obsidian surface does for `Obsidian.exe`; `resolve` and the request and answer files are the Obsidian surface's. The extension in `plugin/vscode/compass-review/` is the mockup's card made real: on activation it scans `tmp/review/` under each workspace folder for requests with no answer, watches for new ones, reveals the panel when one arrives, and writes `<id>.verdict.json` beside the request. Edits count only from `onDidChangeTextDocument` on a listed file while its editor has focus. `engines.vscode` is `^1.85.0`, which Cursor accepts. `plugin/vscode/build_vsix.py` packs the `.vsix`, shipped beside the extension. `self_update.py` and the setup skill copy `plugin/vscode` into `.claude/vscode` as they copy `plugin/obsidian`, so an installed project carries the `.vsix`. Requests live under `<folder>/.compass/tmp/review/`, `<folder>` being the folder holding `.compass`. The node tests stub the `vscode` module and run the cases `plugin/obsidian/tests/test_main.js` runs for the Obsidian card.
- TASK-224: `review_editor: vscode` is set in this repo's `plugin.yaml`; `compass review --install` puts the extension in; three committed files of this vault are sent with `--why`. Recorded: which window came forward, the clicks and minutes, the answer's `files` and `comments`. Then `review_editor: cursor` and the same. The setting is removed afterwards so this repo goes back to Obsidian.
