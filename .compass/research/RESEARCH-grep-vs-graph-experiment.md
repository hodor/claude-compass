## Question

SPEC-011's D-02 gates the spec on an empirical test: can grep/ripgrep plus the existing `compass` CLI answer SPEC-011's five named query classes (backlinks/orphans, impact-of-change traversal, decision lineage, k-hop neighborhood, health analytics) correctly and cheaply on the live `.compass` vault? If yes, SPEC-011 is rejected rather than built. This experiment produces that evidence, and separately checks what it implies for SPEC-012 pillar 2's lesson retrieval.

## Methodology

For each of the five classes, 1-2 concrete questions were posed against this vault. Ground truth was established by careful manual reading: full `depends_on:` frontmatter extraction across all 65 vault markdown files (excluding `.compass/tmp/`), targeted `Grep` passes for exact artifact names and D-NN citation strings, and direct reads of `index.md`, `active.md`, `tag-index.yaml`, and the artifacts under test. The same grep/ripgrep calls used to build ground truth are the ones an agent would issue mid-session (good patterns: literal-name search, alternation regexes, `-n`/content mode) - this is not a strawman pass. The existing `compass` CLI (`F:/claude/plugins/compass/.claude/cli/compass`, since it is not on PATH) was inventoried via `--help` on every subcommand and by grepping `commands/validate.py` for orphan/backlink/hub logic.

## Findings

1. **Single-target lookups (backlinks-to-X, D-NN citation search) are grep-sufficient today (HIGH).** One literal-string or exact-D-NN-string `Grep` call returns a correct, low-noise answer in one round. This covers half of class 1 and all of class 3.

2. **Decision lineage is already CLI-native, not just grep-answerable (HIGH).** `compass decisions <doc>` and `compass coverage <plan> [--against <doc>]` exist and were built by PLAN-004/ADR-007 specifically to answer "which plan tasks cite this decision" mechanically, off the agent token budget. This class needs no new build under SPEC-011 at all.
   - `F:/claude/plugins/compass/.claude/cli/compass --help` - lists `decisions`, `coverage` among 14 commands.
   - `.compass/plans/PLAN-004-decision-coverage.md:57-95` - TASK-023..029 build exactly this mechanism.

3. **Orphan detection and impact-of-change traversal are grep-marginal: correct but costly and fragile (HIGH).** Both required multi-round grepping (2 and 5 tool calls respectively in this experiment) and, critically, manual disambiguation between structural edges (`depends_on:` frontmatter, real `[[wikilinks]]`) and narrative prose mentions of an artifact's name that are not graph edges. Neither failure mode is caught automatically by grep; an agent under time pressure could easily over- or under-count.

4. **k-hop neighborhood with named edge types requires knowing the vault's edge taxonomy up front (MEDIUM-HIGH).** Answering Q4 correctly required checking three independent mechanisms (body-text grep, frontmatter read, `tag-index.yaml` reverse lookup) that an agent would not know to combine unless briefed on SPEC-011's five-edge-type model itself. Tag-hyperedge neighbors in particular are structurally invisible to a grep for the seed artifact's name - they only surface by first reading the seed's own `tags:` field, then reverse-querying each tag.

5. **Tag hyperedges are already queryable via the existing cold-tier tag-index, no new mechanism needed (HIGH).** `.compass/meta/tag-index.yaml:121-127,512-515` already stores tag -> doc-list buckets generated by `compass sync`. This directly answers one of SPEC-011's own open questions ("whether tag hyperedges join the first version") - they already have a queryable substrate today, just not one wired to the other four edge types in one query.

6. **Health analytics (hubs, fragmentation, density) is the one class grep genuinely fails at (HIGH).** Hub ranking demanded reading a single 20.7KB grep dump (too large to inspect inline, had to be persisted and re-read) and hand-tallying 40 edges with no verification - exactly the "agent-token crawl" SPEC-011's problem statement calls out by name for vault-health's orphan/backlink step. Fragmentation and density have no grep-expressible primitive at all; they require actual graph traversal (BFS/union-find), which is a categorically different capability than pattern matching.
   - `F:/claude/plugins/compass/.claude/cli/commands/validate.py` - grepped for `orphan|backlink|hub|fragment`, zero matches; confirms none of this exists in the CLI today.

7. **`depends_on:` grep has a real frontmatter-vs-body ambiguity (MEDIUM).** A plain `Grep` for `depends_on:` matches both the intended frontmatter graph edges and unrelated per-task `depends_on: TASK-0NN` fields inside plan bodies (`.compass/plans/PLAN-002-compass-cli-implementation.md:54-132` alone contributes 12 such false-positive-shaped lines). An agent must know to restrict matches to the first ~15 lines of a file or use a more specific anchor to avoid contaminating a graph query with task-sequencing noise that has nothing to do with document-level dependencies.

8. **`compass unit-check` is already a working, narrow proof that mechanical `depends_on`-graph traversal belongs in the CLI (MEDIUM).** It groups artifacts by shared `depends_on` target into type-spread promotion candidates - a real (if single-purpose) graph computation already running natively and instantly, correctly matching the manually-tallied hub data in this experiment (SPEC-001 dominates every candidate cluster). This is existing precedent for "graph computation in the harness," just scoped to one query shape, not evidence that the broader need is unfounded.
   - `compass unit-check` output - 7 candidates, SPEC-001 cluster has 33 members, consistent with its 17 raw inbound `depends_on` count from Finding 6's tally.

## Contradictions

None. The classes split cleanly: literal lookups and D-NN citation search are grep/CLI-sufficient; ripple traversal and k-hop neighborhoods are grep-marginal (correct but costly and disambiguation-dependent); hub/fragmentation analytics is grep-insufficient.

## Erratum (2026-08-05, independent recomputation)

- **Q2's ground-truth 2-hop set is wrong in both directions.** SPEC-011 and SPEC-012 reach a hop-1 node only through prose mentions, not through `depends_on` or wikilink structure, so they are not 2-hop members; ADR-005 (`depends_on` ADR-004) and PLAN-003 (`depends_on` SPEC-010) are genuine 2-hop dependents the tally missed. The hop-1 set and the hub tally (Q5a) reproduce exactly. This strengthens Finding 3 rather than weakening it: the structural-vs-prose confusion the experiment identified as a risk for agents under pressure occurred inside the experiment's own careful conditions, so the Q2 verdict overstates grep - the hand answer was not merely costly, it was wrong. The recorded set must not be used as a validation answer key; it stands only as an illustration of the hand-tally failure mode.
- **Finding 2's cited path does not support its claim.** The `decisions`/`coverage` commands exist in `plugin/cli/commands/` (what ships), but this repo's local install at `.claude/cli/` is stale and lacks them, so the citation of the `.claude` path is wrong as written. The finding's conclusion stands; any validation run in this repo must refresh the local install first or invoke `plugin/cli/compass` directly.

## Gaps

- This experiment ran on a 65-document vault, well below any scale where grep's linear re-scan cost would become prohibitive in wall time; the token-cost argument (Finding 6) holds at this size and would only worsen, not improve, as the vault grows.
- Density/fragmentation ground truth (Q5b) was not computed by brute-force BFS for a checkable numeric answer, since no grep-only approach could be honestly attempted against it; the verdict rests on the absence of any grep primitive for the computation, not on a failed grep attempt.

## Recommendation (evidence for Roger's D-02 decision)

The premise is not uniformly true. Two of five classes (single-artifact backlinks, decision lineage) are already grep-sufficient or CLI-native and need no new build. Two classes (orphan detection, impact-of-change traversal) are grep-marginal: answerable, but only through iterative multi-round greps with manual structural-vs-narrative disambiguation that a real agent could get wrong under normal working pressure. One class (health analytics: hubs, fragmentation, density) is grep-insufficient outright - hub ranking already crossed into the "agent-token crawl" anti-pattern SPEC-011 was written to eliminate, and fragmentation/density has no grep-expressible answer at all.

This does not support a blanket rejection of SPEC-011 under D-02's stated bar ("if grep plus existing CLI answer them correctly and cheaply, this spec is rejected"), because that bar is not met for classes 2, 4, and 5. Nor does it support building the full five-query-class harness as scoped, since classes 1 (partially) and 3 are already solved. The evidence points toward a narrower SPEC-011: skip backlink-to-single-artifact and decision lineage (already covered), and prioritize health analytics (the only class with zero grep primitive and the clearest agent-token-crawl cost) and impact-of-change traversal (the class the planner most directly needs per SPEC-011's "who is affected" section) if the spec proceeds at all. Orphan detection and k-hop-with-named-edges sit in between: worth building only if bundled cheaply with whichever of the above two is chosen, not as standalone justification.

### Implication for SPEC-012 pillar 2 (lesson retrieval)

Grep/tag matching suffices; no graph substrate is needed. `.compass/meta/lessons-catalog.yaml` holds 14 flat lesson rows, each carrying its own `tags`/`area`/`category`/`summary` fields, with no `depends_on` or wikilink edges between lessons at all - lessons do not participate in the specs/plans/ADRs `depends_on` graph the other four classes were tested against. Surfacing relevant lessons at the point of work is a keyword/tag match over 14 rows, an operation well inside plain grep's comfort zone and far below [[RESEARCH-rag-fit-for-large-vaults]]'s own ~300-500 doc threshold for even considering vector retrieval. SPEC-011, even fully built, would not directly serve this pillar since its five edge types are artifact-graph edges, not catalog-row relevance ranking.
