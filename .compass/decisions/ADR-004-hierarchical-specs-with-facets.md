## Status

Approved. Implementation tracked in `PLAN-003-hierarchical-vault-implementation.md`.

## Context

The flat vault scales poorly: root index inflates with every new spec, multi-perspective specs have no good home, and large feature specs become mid-context blobs that trigger the documented lost-in-the-middle accuracy penalty (Liu et al. TACL 2024, 20-30 point degradation across frontier models). [[SPEC-003-hierarchical-vault-organization]] frames the need; [[RESEARCH-hierarchical-knowledge-base-design]] gathered 11 verified findings across MemGPT, RAPTOR, Ranganathan's faceted classification, and Denning's working set theory.

## Decision

Adopt a four-part architecture for the Compass vault:

### Part 1: MemGPT-style three-tier memory

- **Hot tier (always in context):** root `index.md` pointers + one-line summaries + active task IDs + lessons catalog tags. Hard cap 5,000 tokens. Positioned at the START of every agent prompt.
- **Warm tier (fetched on navigation):** folder-level `index.md` files. Each is a RAPTOR-style summary node above its child specs - reflects what the branch is for, lists children with one-line each.
- **Cold tier (fetched only on demand):** full spec bodies and historical artifacts. Agent reaches these by following a pointer from hot or warm.

Movement between tiers is query-driven via explicit reads, modeled on MemGPT's page-fault analog. Eviction from hot occurs at occupancy thresholds.

### Part 2: Hierarchical folder layout

A spec earns its own folder when it has 3+ sub-concerns OR its body would exceed roughly 2,000 tokens. The folder's `index.md` is the parent spec at that level. Numbering is local per folder (resets at each level). Path is identity. Children inside follow the same rule recursively.

```
.compass/specs/
├── SPEC-001-flat-thing.md
├── SPEC-002-tile-editor/
│   ├── index.md
│   ├── SPEC-001-master-material.md
│   └── SPEC-002-brush-system/
│       ├── index.md
│       └── SPEC-001-stroke-rendering.md
```

### Part 3: Faceted tag overlay

Every spec carries `tags: [facet1, facet2, ...]` in frontmatter. The tags are folksonomy (free-form, not controlled vocabulary). A spec belongs to whatever facets describe it: a master material spec is `tags: [rendering, tile-editor, materials, shaders]` even though its folder is `tile-editor/`.

A generated `.compass/meta/tag-index.yaml` maps each tag to the specs that carry it. This is the multi-parent retrieval primitive. The agent reaches multi-perspective specs by reading the tag index, not by crawling folders.

### Part 4: Admission control

Before adding any new content to the hot path, Compass checks the working set: how many specs has the agent touched in the last N turns, and would adding the candidate push the hot path over its 5,000-token cap? If yes, refuse. The agent is told to use the tag index or folder navigation instead.

Working set is tracked in `.compass/meta/working-set.yaml` - rolling window of (spec_path, turns_ago) entries.

## Decision details on the four open questions

1. **Auto-generated vs hand-curated branch summaries.** Auto-generated by an LLM pass at write time, with human approval gate via `/compass:promote-spec` or `/compass:taxonomize`. Cheap and consistent; humans approve before commit.
2. **Tag vocabulary.** Folksonomy. Free-form `tags:` per spec. Periodic `/compass:consolidate` runs a vocabulary pass that proposes synonym merges and tag retirements - human approves.
3. **Lessons catalog in the hot path.** Stays as a single file (`.compass/meta/lessons-catalog.yaml`) in the hot path. Tags on specs are facets of the spec, not duplicates of lesson tags. Lessons themselves carry their own tags; the two tag namespaces are independent but can share words (no rule against it).
4. **Admission-control signal.** Working-set heuristic (specs touched in last 10 turns, configurable) plus a 5,000-token hard ceiling on the hot path. Both must hold.

## Alternatives considered

- **Stay flat.** Rejected: the documented failure modes (capacity collapse, lost-in-the-middle, multi-parent) are not theoretical, and they get worse with vault size.
- **Strict tree, no tags.** Rejected: Ranganathan demonstrated in 1933 that strict hierarchy cannot accommodate multi-perspective content. Modern UX research (NN/g polyhierarchy) reaches the same conclusion.
- **Tags only, no tree.** Rejected: spec sizes vary by orders of magnitude. Without folders, big features become single 10k-token files that trigger lost-in-the-middle on every read.
- **Global numbering across the tree.** Rejected: breaks subtree portability. With local numbering, a subtree can be moved or extracted without renumbering.
- **Predictive prefetching of likely-needed specs.** Rejected: unvalidated for production agent memory. MemGPT's reactive page-fault model is the field-standard pattern.

## Consequences

**Easier:**

- Hot path stays bounded regardless of vault size.
- Multi-perspective specs are reachable from any angle they belong to, without restructuring.
- Large features split into folders without the parent becoming useless.
- Migrations are non-destructive: existing tags and references survive when new content arrives.

**Harder:**

- New infrastructure: tag-index file, working-set tracker, RAPTOR-style auto-summarization. More state to maintain.
- Folksonomy tag sprawl is a real risk. Periodic consolidation is the mitigation, but it depends on someone running it.
- Branch summary drift: folder `index.md` files can fall out of sync with their children. Index-sync flags staleness, consolidate refreshes.
- Validation must show the 30% read-reduction claim is real. If empirical measurement shows the hierarchy adds overhead without benefit, the design is wrong.

## Load-bearing risks

- The fanout heuristic (8-20 children per folder) is derived, not published. Needs empirical tuning. Cache-conscious CSB+ trees suggest going wider; LLM attention cost per token suggests going narrower. Real Compass usage will tell us which dominates.
- The 2,000-token threshold for "spec earns a folder" is a design heuristic synthesized from RAPTOR + lost-in-the-middle + capacity collapse. Not directly published. Needs tuning.
- The hot path 5,000-token cap is conservative but arbitrary. Should be re-evaluated after the first production vault hits 100+ specs.
