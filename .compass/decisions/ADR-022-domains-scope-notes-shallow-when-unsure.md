# Domains, Scope Notes, and the Folder as the Listing

## Context

[[SPEC-022-vault-organized-per-domain]]: the filesystem is a taxonomy, recursive, indexes explain meaning while the folder shows its own first level (D-03, D-08), reorganization suggested by the harness rather than remembered by the human (D-07). [[RESEARCH-taxonomy-for-unambiguous-placement]]: filers inherently disagree (10-60%), so unambiguity is engineered - few broad top levels, scope notes at the point of doubt, one primary home with facets as the multi-parent axis, corpus-warranted categories, mechanical split triggers, human-curated tops. Listings are never materialized into index files: a stored copy of a directory listing is the derived-store shape [[ADR-018-graph-queries-jit-over-markdown]] rules against for the graph, and SPEC-022 D-08 rules against for folders.

## Decision

- **D-01:** Domains are orthogonal, and top-level generality scales with depth (SPEC-022 D-09). No forced count - a handful is a suggestion, and ten completely orthogonal top-level domains are fine. The rule has two parts: orthogonality - no document plausibly belongs under two siblings, with scope notes resolving the residual edge cases - and the depth gradient - the deeper a subtree grows, the more generic its top-level name must be, so everything accumulating below still fits without re-rooting. Domain names are bare descriptive words a finder would reach for, unique vault-wide: `make-domain` refuses a name any other type dir already uses as a domain, because two areas both named `distribution` re-create on the root surface the exact ambiguity this spec exists to end. Domain names are the human's call at proposal time, always.
- **D-02:** Every domain index carries scope notes, two tiers, in a `## Scope` section: `Class here:` lines naming what belongs, `Class elsewhere:` binding redirects (`X -> [[other-domain]]`), and advisory `See also:` pointers. Scope notes are hand-authored placement judgment; nothing regenerates them. A domain is never created with an empty Scope: `make-domain` requires `--class-here "<line>"` the same way shape commands require `--reason`, and `validate` warns `empty_scope` on a domain index whose Scope has no Class-here line - an empty promise at the point of doubt is worse than no section.
- **D-03:** One physical home; tags stay the cross axis. No document ever exists in two places. Multi-domain membership is expressed by tags (ADR-004's post-coordinate design, validated by the research) and by advisory see-alsos in scope notes.
- **D-04:** File shallower when unsure. A document that clearly belongs to a domain but ambiguously to its subdomains lives directly in the domain folder; stopping at the certain ancestor is the stated rule in the placement contract. Top-down error propagation makes a wrong deep placement worse than a shallow correct one. A type dir below the ceiling has no domains at all - the root is the correct home for a small vault, and no hint is written where there is nothing to be uncertain about.
- **D-05:** Domains are born from warrant and splits are suggested by ceiling. A domain is created only when existing documents justify it, never speculatively. `compass validate` warns `folder_over_ceiling` when direct children exceed the ceiling (tunable default 12) - counted by path so the type dirs themselves are covered, and scoped to taxonomy-governed dirs only (`specs/`, `research/`, and domain folders; `lessons/` is catalog-indexed and `plans/`, `decisions/`, `handoffs/`, `prs/` are out of scope this round, so they are exempt rather than allowed to become permanent ignored noise). Per SPEC-022 D-07, the warning is a suggestion surfaced to the human every time validate or doctor runs - reorganization is never something the human must remember to trigger, and never automatic.
- **D-06:** Thin domain indexes are `type: domain` - frontmatter: title, type, status (active), summary, tags, created, updated (status included: it is CORE_REQUIRED and its absence is a validate error) - plus the `## Scope` section. Nothing else: the index is identity and scope. A promoted natural parent stays a folder spec. `compass make-domain <type-dir>/<path>` creates the folder, template, and sizing-log row, at any nesting depth. This amends ADR-021 in two named places: D-01's fiat that every domain index is "the spec document itself" (the spec template's Problem framing does not fit a topical bag), and D-04's "no new migration machinery" (the thin domain had no creating command: promote needs an existing source file, make-unit is root-only - [[RESEARCH-taxonomy-for-unambiguous-placement]] design Finding 3). ADR-021 is stamped `amended_by` accordingly.
- **D-07:** The folder is the listing; no index materializes it (SPEC-022 D-08). An index.md - domain, folder spec, or unit - carries what `ls` cannot say: identity, scope, shared decisions. Member listings are read from the filesystem (`ls`/Glob, one tool call, always true) and the whole-tree view with summaries is `compass tree`, computed at invocation like the graph queries - the JIT-over-derived-store principle of [[ADR-018-graph-queries-jit-over-markdown]] applied to listings. The hand-maintained `## Children` convention retires: obsidian stops mandating it, `make-unit` stops writing it, and existing sections are removed when their folder is next touched - they are derived listings whose every fact lives in the filesystem and in each child's own `summary:` frontmatter, so removal is tiering, not loss. Two boundaries: the root `index.md` keeps its entry lines - it is the preloaded boot map, the one place a session has no tool call yet - and plain type dirs get no index.md of their own (their meaning is their name; the domains below them carry the scope notes). This supersedes the non-LLM half of [[SPEC-005-index-auto-maintained-and-mirrored-per-folder]]: the per-folder listing it specified is read live from the filesystem instead of maintained.
- **D-08:** New links to artifacts below a domain are written path-qualified (`[[specs/vault-structure/SPEC-001-name]]`), and sync's own generated links - domain lines in the root index included (`[[specs/vault-structure]]`) - are always the vault-relative form. Existing bare-stem links remain valid: resolution is name-to-path and survives every move, so nothing is backfilled, and validate warns on a bare link only when it is actually ambiguous. The record-name defect underneath (nested non-loose records carry names without their type dir, so same-named domains across type dirs cross-contaminate child counts) is fixed as part of this decision: nested records get vault-relative names.
- **D-09:** `taxonomy_hint:` is frontmatter, written at creation when placement is uncertain (the authoring agent files shallower AND records the hint - it understands the artifact better than any later pass). Two consumers, so the queue drains everywhere: consolidate's Structure pass takes hints as its work queue, and `validate`/`checkup` surface `taxonomy_hints: N pending` as a standing suggestion in every vault, cap breach or not (SPEC-022 D-07). A hint clears when acted on - moved, or confirmed fine where it sits.
- **D-10:** The sync loop guard matches exact root-relative paths (root `index.md` and the meta files), replacing the endswith match that silently swallowed every nested index.md agent-write - a live bug: writing a folder spec's own index today triggers no sync and no capture signal.
- **D-11:** Documentation aligns in the same release: obsidian gains the placement contract (D-01..D-04, D-08), scope-note authoring, and the folder-is-the-listing convention (ls for contents, index for meaning) replacing the Children mandate; promote-spec's false "CLI refuses" claim is corrected; methodology/setup's "flat, one file each" trees are rewritten; `compass tree` is restored as the whole-tree view (retired unused in ADR-017, now load-bearing: it is both the answer to "the index used to show me everything" and the summaries view `ls` alone cannot give).

## Consequences

- The filer's procedure: root index domain lines (hot-path resident, their summaries written as class-here digests so the obvious case costs zero extra reads) -> on doubt, open the domain index for its Scope note -> file shallower if still unsure -> hint if genuinely uncertain. +1 read on the non-obvious cases only.
- The finder's procedure: root index -> `ls` the domain (or `compass tree` for the whole picture) -> open the file. Every level is the filesystem itself; nothing can be stale.
- One write point per change: the file moves, and that is the whole change. No index rewrites ripple from a child write, so no stale-anchor edit failures and no git churn in files nobody edited.
- Nothing depends on filers agreeing: scope notes, facets, and shallow placement all tolerate the measured 10-60% disagreement, and the LLM-filer consistency question stays open by design - the migration's acceptance drills produce its first datum.
- The migration must shrink the root index, not grow it: member lines whose folders now carry them are replaced by domain lines. Every removed line was a copy of its artifact's own `summary:` frontmatter (the index rule), so the never-destroy audit is "every removed line's artifact exists at its new path with its summary intact".
