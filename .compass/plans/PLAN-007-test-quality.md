# Test Quality Instruments (Authoring Bar, Test-First Station, Admission Filter, Diagnostic Mutation)

## Goal

Give [[SPEC-013-test-quality]]'s admission bar a place to stand. Today "adversarial" is a word in an agent prompt with no operational definition, no mechanical check, and - as this plan discovered while reading the current flow - no reliable moment at which the tester actually runs. This plan stations four instruments at four different points, exactly as D-03 orders them: the D-01 bar plus the boundary-and-fixture criterion govern authoring, a stdlib-`ast` filter gates admission, diff-scoped mutation is an on-demand diagnostic that never blocks, and a seeded-defect probe validates the bar itself against the 13/15 baseline already measured. The procedural half of D-04 lands alongside it: tests are authored from the task's spec before the implementation exists, and the failing tests are committed and checkpointed so that a later edit to them is visible rather than silent.

Grounded in [[RESEARCH-test-quality-synthesis]] (the station model, the build order, and the do-not-build list), [[RESEARCH-test-quality-craft-and-practice]] (the per-test-type design brief and the adopted procedures), [[RESEARCH-test-quality-literature]] (the misguidance effect and the insufficiency of prompt-only bars), [[RESEARCH-test-quality-tooling]] (the stdlib-`ast` path and the Windows constraint), and [[RESEARCH-test-quality-empirical]] (the measured baseline this plan must not regress).

## Desired End State

- A `test-design` skill holds the operational admission bar in one place: what a single test must demonstrate to exist (the defect class it catches, named in a docstring before any test code), the four classes that never qualify, the boundary-and-fixture criterion as a co-equal second rule, and the per-test-type design brief. The tester loads it; the validator audits against the same names.
- The tester runs at two stations per code task. Before the builder: it authors tests from the task's spec, acceptance criteria and automated-verification bullets, with no implementation in existence to be misguided by, and runs them red. After the builder: it runs the full suite, checks the checkpoint, and owns a named set of implementation-visible defect classes the spec could not have reached.
- `compass test-checkpoint` commits and records those failing tests before implementation begins, then classifies every later change to them as `added-only` or `modified` by comparing ASTs read back out of git. A builder that edits an assertion, appends a skip decorator, or shadows a checkpointed helper is detected mechanically, not by an agent noticing.
- `compass test-smells` walks test files with stdlib `ast` and reports empty tests, duplicate asserts, literal-only assertions (gate) and assertion-free tests and Assertion Roulette (advisory). The tester runs it on its own output before reporting; the validator runs it over the diff. Gate findings exit 1, advisory findings do not, and it never exits 2.
- A fleet census answers whether the 841-test suite that motivated SPEC-013 is actually bloated, so the admission filter ships either as a guard with evidence or with its first patient named.
- The validator's report carries a test-quality section with real `Command run:` evidence, report-only, in the same shape as the decision- and lesson-coverage audits it already runs.
- A paired seeded-defect experiment answers SPEC-013's own falsifiable hypothesis: the same three modules, the same 15 defects, tests re-authored under the new bar against the tests written without it.
- `compass mutate` exists as a diff-scoped, non-blocking diagnostic **if and when Phase C is unparked**. It is designed and costed here, not built now.

## What We're NOT Doing

The do-not-build list is carried verbatim from [[RESEARCH-test-quality-synthesis]] section 6, plus four scoping exclusions this plan adds. Each is killed by evidence, not by budget.

- **A mutation-score threshold or gate ("must reach N%").** Literature F2 (the proxy collapses precisely when the code under test may be buggy, which is always the case here) and F3 (equivalent mutants have no complete solution), and killed directly by synthesis section 2c: 63.6% was measured on a suite that is genuinely strong. D-03 states it as policy.
- **mutmut, Mull, cosmic-ray, or any WSL-requiring tool as a dependency.** Tooling F1 is a direct probe: mutmut refuses to start natively on Windows and the blocker is architectural. F15 for Mull. F5 leaves cosmic-ray unverified, which is not a pass.
- **Coverage-overlap test deduplication or pruning.** Literature F6: minimization by coverage overlap "can severely compromise the fault-detection effectiveness" of the reduced suite. Empirical F8 confirms locally: 20 tests failed on one seeded defect and looked redundant, but three sibling defects were caught by disjoint subsets of 2, 1 and 3. This is the intuitive thing to build and the evidence specifically kills it.
- **Retroactive LLM grading of every existing test, fleet-wide.** Literature Gap 3 (no cheap technique exists) and empirical F3 (grading 310 tests by hand yielded 3 WEAK, 0 FAIL - about 1%). D-05 makes this policy: a guard, not a cleanup campaign. What survives of SPEC-013's retroactive-assessment Need is the **on-demand census** in TASK-065 - one project, measured when there is a reason to measure it - and that is stated as the answer to the Need, not as a deferral of it.
- **A proportionality formula** (tests per branch, per public method, per behavior). Literature Gap 4 and ACH's argument for defect-class enumeration instead. D-01 already forbids suite-size judgment in either direction, so a formula would contradict the spec it serves.
- **Mandating property-based testing.** Literature F20 is medium-confidence and carries its own caveat: LLMs do measurably worse when the specification is abstract. Allowed and given design guidance, never required.
- **Mechanical detection of fixture aliasing.** The rule ("a fixture value never equals the constant it overrides") is stated as authoring guidance in the `test-design` skill, per D-04. Detecting it mechanically requires resolving a default value across modules and would produce false positives on every legitimately-coincidental number. Prose only.
- **String-literal mutation operators, by default.** Synthesis section 2d: string-literal mutants are where the equivalent-mutant residue concentrates - a mutated log-row key or payload field name produces a mutant no test can legitimately kill, so the survivor is uninformative by construction rather than merely noisy. (The 77% noise figure from section 2b is not the argument; full-suite scoping retires it.) Available behind `--strings`, off by default.
- **A language-agnostic core.** D-06 defers it explicitly until a second language supplies evidence. Every module here is Python-only and says so.
- **Fuzzing and contract tests.** Craft findings 7 and 8 record both as techniques with a condition attached (untrusted external input; independently-deployed components), neither of which Compass's single-process CLI currently meets. Recorded in the skill as the trigger to revisit, not built.
- **Any of this on a hook path.** The smell filter is milliseconds and the mutation runner is minutes; neither belongs in the latency budget of a write hook. Invocation is by agent or human, always.

## Constraints (all tasks)

- CLI: stdlib only, never exits 2, `python`/`python3` both supported. All file writes route through `vaultlib.write_text_lf`, which is the single writer that enforces LF endings. Tests in stdlib `unittest` under `plugin/cli/tests/`.
- **"Suite green" has a mechanical definition for the duration of this plan.** Because checkpointed failing tests live on the working branch before their implementation exists, a bare `python -m unittest discover -s plugin/cli/tests` will report failures that are the plan working correctly. Green means **no failures outside the open checkpoint set**, where that set is exactly what `compass test-checkpoint open-ids` prints: the checkpointed test ids of tasks not yet landed. Every "full suite green" in this plan's automated-verification bullets carries that definition, and so does every one in `tester.md`, `build/SKILL.md` and `validator.md` after Phase A.
- Behavior changes land in `plugin/`. A change is not live in this repo until the matching file reaches `.claude/`; Phase D carries the refresh step.
- Mechanical work stays off the agent budget ([[SPEC-004-mechanical-work-off-the-agent-budget]], [[LESSON-no-agent-bookkeeping]]). No task may put into agent prose a judgment a script can make. This is why the checkpoint comparison is a CLI AST classifier rather than "the tester reads `git diff` and decides".
- **The tester's own tests are held to the bar they enforce.** Every test written for the modules in Phase B must clear D-01 and the boundary criterion, and `compass test-smells` must report zero gate findings on them. A checker that cannot pass its own check ships a contradiction.
- The testing mandate is not weakened anywhere. SPEC-013's non-goal is explicit: this is about quality, never permission to skip.

## Mechanism decisions this plan makes

The spec adopted the procedures (D-04) without saying how they fit a build loop where the tester runs after the builder. These are the choices the tasks implement.

- **The tester runs twice, and the first run is before the builder.** For any task whose `files:` include executable source, `/compass:build` spawns the tester in **pre-build** mode with the task body, its acceptance criteria, and its automated-verification bullets - which are the concrete input/expected pairs the equivalence classes get derived from - and nothing else. The implementation does not exist yet, so the misguidance source literature F15 identifies is not merely discouraged, it is absent. A task too abstract to derive equivalence classes from is reported back as a **plan defect** for the orchestrator to amend, which is D-04's authoring contract failing upstream and made visible rather than absorbed. After the builder finishes, the same agent type runs in **post-build** mode against a named, different set of defect classes.
- **The two stations are scoped differently, not sized differently.** Pre-build owns everything derivable from the spec: equivalence classes, boundaries, contract violations. Post-build owns what only the implementation can reveal - timezone and encoding contracts, branches the implementation introduced, private helpers with their own edge cases. The worked examples are the `_now()` tzinfo survivor and the L3 defect from the empirical probe: both are invisible from the task text and both are unmistakable once the code exists. Post-build must not re-derive pre-build's equivalence classes; that, not brevity, is the check.
- **Git is the record of authority; the JSON is an index.** `record` requires a checkpoint commit and stores its SHA; `verify` re-reads the checkpointed content with `git show <sha>:<path>`. Deleting or editing the untracked JSON therefore cannot launder a modification, and a commit SHA that is absent from the log is itself an exit-1 finding.
- **The checkpoint commit lands on the working branch, before the builder spawns.** Builders run in SDK-managed worktrees whose branch does not exist until the builder is spawned, so the checkpoint cannot land on the task branch. It lands on the orchestrator's working branch, and the builder is spawned only after the commit exists, so the worktree fork contains it ([[LESSON-subagent-worktrees-fork-stale]]). The second half of that lesson is also mechanized: the spawned builder fast-forwards to the working branch and confirms the checkpointed test files are present before writing any code, halting loudly if they are not.
- **Tamper evidence is an AST comparison, not a line comparison.** `added-only` requires that every checkpointed test function is byte-identical *including its decorator list*, that every added module- or class-level statement is a new `FunctionDef` or `ClassDef` rather than an `Assign` or bare `Expr`, that the checkpointed `(class, test_name)` id set is unchanged, and that no added line rebinds a def, class, or module-level assignment target present in the checkpointed content. Shadowing is a modification and the report names the shadowed symbol. A line-level comparison passes all four of those attacks.
- **Passing is checked at the run level, not only at the file level.** A checkpointed test that still exists verbatim but is skipped, errored, or never collected has been neutralized just as effectively as one that was edited. `verify --against-run <evidence>` requires every checkpointed test id to appear PASSED in the post-build run.
- **The checkpoint is verified at every fix-loop cycle, against the worktree that is actually changing.** The failure mode Anthropic's own guidance names (craft finding 12: the agent changes tests to make them pass) is a fix-loop behavior. `verify --tree <worktree path>` is what makes the per-cycle check non-inert - without it the check re-reads the orchestrator's checkout, where nothing is changing, and reports `unchanged` through an entire loop of tampering. A mandatory post-merge verify runs against the merged branch.
- **The station is conditional on file type, with no new plan grammar.** A task whose `files:` are agent templates, skills, or docs has no executable surface to test first; `build/SKILL.md` states the condition on the files themselves. Inventing a `test_first:` task field would add ceremony to every plan to express something the file list already says.
- **Severity, not a second command, separates gate from advisory.** `compass test-smells` emits both classes in one run and exits 1 only on gate findings, so a check whose precision has not yet earned gate status still gets seen.

- [x] TASK-052: `compass test-checkpoint record | verify | open-ids` - complexity: L, depends_on: none, files: [plugin/cli/commands/test_checkpoint.py, plugin/cli/maincli.py, plugin/cli/tests/test_test_checkpoint.py], decisions: [SPEC-013-test-quality/D-04, SPEC-013-test-quality/D-06], lessons: [LESSON-no-agent-bookkeeping, LESSON-scratch-vaults-need-compass-dir]
  - **`record TASK-NNN <test file>... --commit SHA [--red-evidence PATH] [--supersede TASK-NNN --reason "..."] [--not-required]`.** The commit SHA is required for a code task: git holds the authoritative copy of the checkpointed content and the JSON at `.compass/tmp/test-checkpoints/TASK-NNN.json` is an index over it (per-file path, SHA-256, the commit, the red-evidence path, a UTC timestamp, and the extracted `(class, test_name)` id set). Checkpoints live under `.compass/tmp/` because that tree is pruning-safe - `sync` and `clean-tmp` glob only extraction logs and capture-log rows, so nothing sweeps them - and because it is gitignored, which keeps a worktree from carrying stale checkpoint state; neither property is load-bearing for integrity, since git is the authority.
  - **`record` also hashes the test-support surface**: fixtures, `__init__.py`, and helper modules under the test root the checkpointed files live in. A change to shared corpus data is a change to what the tests assert, and without this the whole guard is bypassable by editing a fixture instead of a test.
  - **`--supersede`** versions a checkpoint rather than overwriting it: the prior version is retained, and `verify` reports against the current version while naming the supersession and its reason. A pre-build test can be legitimately wrong, and without a correction path the first such test poisons `verify` permanently and trains everyone to ignore exit 1.
  - **`verify TASK-NNN [--tree PATH] [--against-run EVIDENCE] [--expect-checkpoint]`.** Content is re-read via `git show <sha>:<path>`, so editing or deleting the JSON cannot launder a modification. `--tree` points the current-state read at a builder's worktree, which is what makes the per-cycle fix-loop check see the files that are actually changing. Classification is AST-based, per the mechanism decision above: `unchanged`, `added-only`, `modified` (naming the changed function, or the shadowed symbol when the cause is a rebinding), or `missing`. `--against-run` additionally requires every checkpointed test id to be PASSED in the supplied run evidence. Exit 1 on `modified`, `missing`, a checkpointed id that is not PASSED, or a commit SHA absent from the log.
  - **Three absence states, distinguished.** `not-required` - a recorded skip for a task with no executable files - exits 0. `no-checkpoint` for a task that has executable files exits **1**: an unrecorded code task is the state this whole mechanism exists to notice, and exiting 0 on it would make the guard silently optional. `--expect-checkpoint` is what the fix loop passes to assert the recorded state is the one it expects. Never exits 2. Vault root resolution goes through `vaultlib.find_vault_root` ([[LESSON-scratch-vaults-need-compass-dir]]).
  - **`open-ids`** prints the checkpointed test ids of every task not yet landed. This is the mechanical definition of the open checkpoint set that "suite green" is stated against everywhere in this plan and in the three agent files it amends.
  - Automated verification: unittest - `record` writes the index through `vaultlib.write_text_lf`; `record` without `--commit` on a code task exits 1; `verify` on untouched files exits 0 reporting `unchanged`; appending a new test function reports `added-only` and exits 0; changing one assertion reports `modified` naming the function and exits 1; **appending `@unittest.skip` to a checkpointed test reports `modified`**; **appending a second def with a checkpointed test's name reports `modified`**; **adding a class-level assignment reports `modified`**; **an added line rebinding a checkpointed module-level name reports `modified` and names that symbol**; deleting a checkpointed file reports `missing` and exits 1; a modified fixture under the test root reports `modified`; editing the JSON to drop a file does not change the verdict (git is re-read); a commit SHA absent from the log exits 1; `--tree` classifies against the supplied tree and not the current checkout; **a checkpointed id present but SKIPPED in `--against-run` evidence exits 1**; `--supersede` retains the prior version and `verify` names it; `not-required` exits 0; `no-checkpoint` on a code task exits 1; corrupt JSON exits 1 with a message and no traceback; `open-ids` prints only unlanded tasks' ids; exit code is never 2 on any of the above.
  - Manual verification: record a checkpoint over a scratch copy of one real test file, edit a single assertion, run `verify`, and confirm the diff output identifies the changed assertion legibly enough to decide "the builder cheated" or "the fix was legitimate" without opening the file. Then delete the JSON and re-run: the verdict must be unchanged.

    - **Empty test** (gate) - a body of only `pass`, `...`, a docstring, or a bare `return`.
    - **Duplicate assert** (gate) - two assertion statements in one test whose `ast.unparse` output is identical **and** with no intervening statement that rebinds a name the assertion reads. The rebinding clause is not a refinement for its own sake: the single hit on the current corpus is a good test that asserts the same invariant across a state change, and without the clause the check's only real-world finding is a false positive.
    - **Literal-only assertion** (gate) - the test never calls into the code under test; it only reads imported constants and asserts them against literals or against each other. Helper-method calls count as calls.     - **Assertion-free test** (advisory) - a `test_*` function with no `assert`, no `self.assert*` call, no `self.fail(...)`, no `assertRaises`/`pytest.raises` context, and no call to a same-module or same-class helper whose name begins with `assert`, `_assert`, or `check`. `self.fail(...)` counts as an assertion, which alone corrects one of the three false positives measured. The remaining two are does-not-raise tests, and the check ships advisory because no convention yet distinguishes an intentional does-not-raise test from a test that forgot to assert.

## Phasing logic

The order is synthesis section 5's, which ranks by evidence strength divided by cost: the prose mechanisms (spec-derived authoring, the boundary criterion) carry most of the value at zero runtime cost, so they ship first and independently of any tooling. The mechanical filter follows because literature F12 says prose alone is insufficient, and it is cheap enough to be second. Mutation is parked because it is the only piece that costs real engineering and, after the review, the only piece nothing else in the plan consumes.

Three deviations from a strict prose-first reading, all deliberate. First, `compass test-checkpoint` (TASK-052) lands inside Phase A rather than with the other CLI work, because Phase A's flow calls it - shipping the instruction before the command would ship an error. Second, the census (TASK-065) sits in Phase A although it produces no plugin change, because its result is Phase B's entry condition and Phase A is long enough to absorb it without adding wall clock. Third, the validator audit is consolidated into a single Phase D task rather than being added incrementally in each phase, so `validator.md` is edited once instead of three times.

Within Phase A, the skill precedes the tester that loads it, the tester precedes the build flow that spawns it, and `builder.md` and the methodology mandate come last because they describe a flow that must already be settled.

Phase D no longer waits on Phase C: TASK-063's paired design needs no mutation runner, and TASK-062 treats the mutation part of its audit as conditional. That is what makes parking Phase C free rather than merely deferred.

## Risks

- **The red working branch.** The checkpoint commit lands on the working branch before any builder spawns, so the branch carries failing tests for the duration of a phase's build. Mitigation: `open-ids` gives "green" a mechanical definition that tolerates exactly those failures and nothing else, so the window is bounded rather than merely tolerated; it closes at the phase merge, where the mandatory post-merge verify runs. **The honest fallback if the human rejects the red window is a side ref**, not "record without committing": recording a hash without a commit provides no tamper evidence at all (git is the authority the whole design rests on) and, worse, delivers no tests to a worktree builder, because uncommitted files do not exist in a fork. The workable alternative is `git commit-tree` writing the checkpoint under `refs/compass/checkpoints/`, which keeps content in git and off the working branch at the cost of a fetch step in every builder spawn. See R2.
- **The builder implements to the tests rather than to the spec.** [[LESSON-test-driven-tasks-dont-discriminate]] measured this directly: when tests fully encode the spec, frontier models read the tests first. That is fine for correctness and bad for the methodology signal, because a builder satisfying assertions is not the same as a builder satisfying intent. Mitigations: `builder.md` keeps the spec as the source of truth and the tests as a constraint; the post-build station owns defect classes the spec could not name; TASK-064's manual verification asks the human whether the flow returned more than it cost.
- **The tester's cost roughly doubles.** Two spawns per code task is a real increase on the largest agent cost centre in a build. Mitigations: prose-only tasks skip the station entirely (most of this plan's own Phase A would), and post-build is scoped to a disjoint set of defect classes rather than a repeat pass. **This cost is tracked and reported, not gated** - TASK-064's manual verification is where it is judged, and there is no automated check that fails on token spend.
- **A noisy filter gets switched off.** A gate that fires on legitimate tests discredits the whole instrument. Assertion Roulette was the presumed offender and has been demoted permanently on measured data (TASK-058). The remaining risk sits with literal-only, whose corrected definition has been measured at 6/420 with 50-100% precision; TASK-057's manual ruling is where the human decides whether that is gate-worthy.
- **Mutation output is unmanageable on first contact.** Retained as a parked risk against TASK-061. Mitigations if unparked: string-literal mutation off by default, diff scoping, `--max-mutants` at 200 (~18 min), full-suite runs, scope-limited labelling, and survivors framed as triage candidates rather than a score.
- **The pre-build red is only an import error.** A test suite written against a module that does not exist fails at collection, which is a weak form of "seen to fail" (craft finding 19). Mitigation: TASK-054 requires the mode to label a collection-only red as such, and the post-build station's `verify --against-run` is what proves the tests were later seen to pass for their own reasons. This is a known limitation of test-first against greenfield modules, not a defect introduced here.
- **The baseline suite was not written by testers.** This is established fact, not a possibility: across 151 commits there are zero test-only commits and zero merges of tester work, and `builder.md`'s "you write no tests" rule was *unenforceable* rather than merely unenforced, because the hook that was supposed to hand off to a tester never existed. [[RESEARCH-test-quality-empirical]]'s 99% PASS grade is therefore a measurement of builder- and orchestrator-written tests. This does not change what to build, and it arguably strengthens the case for Phase A: the station being introduced is not a refinement of an existing handoff, it is the first one. It does change how TASK-063's paired comparison must be read, and that caveat is stated in the task.

## Inherited questions resolved

SPEC-013's four open questions were addressed to research and are answered in the five research documents; the questions below are the ones [[RESEARCH-test-quality-synthesis]] section 4 raised for Roger. Three are settled by the spec's own decisions. The rest are resolved here and carried into the rulings sheet.

- *Q1: guard or cleanup?* Settled by D-05: a regression guard protecting a measured-good state. No task in this plan regrades or prunes an existing suite. SPEC-013's retroactive-assessment Need is answered by TASK-065's on-demand census of one named project - that is the surviving form, and it supersedes wholesale regrading rather than postponing it.
- *Q2: is the trace and observability layer in scope for the admission bar?* **Resolved here; see R4.** In scope. The capture-log rows are a contract, not debug output: `sync` prunes them on a retention horizon, `capture-stats` parses them into fire and write rates, and the capture commands read them back. Code that another module parses is code whose field names are part of an interface. The consequence is bounded by D-05 - the existing thinness synthesis section 2a found is recorded as an observation and not a cleanup task. The `test-design` skill states this as a general rule rather than a Compass-specific carve-out: if another module parses the output, its shape is behavior.
- *Q3: may a mutation result ever block?* Settled by D-03 and implemented literally in TASK-061 if it is ever unparked: exit 0 whenever the run completes, survivors or not, and a unittest asserts the output contains no percentage.
- *Q4: where does the mechanism live?* Settled by D-06: the compass CLI. Every new command is a CLI subcommand invoked by an agent or a human, and none is on a hook path.
- *Q5: language scope?* Settled by D-06: Python-first, and the language-agnostic core waits for a second language's evidence. Recorded in the not-doing list so a future reader knows it was declined rather than forgotten.
