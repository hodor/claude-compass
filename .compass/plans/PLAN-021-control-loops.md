# Control Loops as Vault Artifacts

This plan implements [[specs/pipeline/SPEC-026-control-theory-for-loops]] on the evidence of [[research/pipeline/RESEARCH-control-theory-for-loops]]. A user, or Compass itself, gets a control loop for a task: a folder in the vault holding the loop's end state, sensor, controller, actuator, golden patterns, feedback file and state (D-01). Each run moves through an explicit state machine, measures itself, stays inside the caps and budget it is given, and stops on its own when it reaches the end state, runs out of budget, or keeps making things worse.

## The waves

**Wave 1** builds the loop's machinery and runs four experiments. The machinery is mechanical and fully known: the vault learns the new artifact type, a library holds the state machine and the run record, the deterministic sensors read cost, turns and time from Claude Code's result event, and `compass loop` creates, runs, pauses and reviews a loop. Compass's own fix loop, where `/compass:build` sends failing tests back to the builder up to three times, gains the sensor it lacks: whether a cycle fixed failures or added them. The four experiments answer what the research could not: how the turn and budget caps behave beyond one turn and across resume, how accurate an agent judging natural-language rules is against planted violations, how accurate rules an agent drafts for ast-grep (a structural code search tool) are, and what a fresh CI checkout of a Compass project runs. The wave ends when a hand-written loop runs live in a scratch project, every experiment has a recorded verdict, and the human has confirmed the manual checks.

**Later**, each experiment's verdict shapes one piece: the judge sensor (gating or advisory), the sensor step that drafts ast-grep rules or asks for them, and the schedule (a GitHub Actions workflow or the local lane). The guided `/compass:loop` skill comes last, because it walks the human through every one of those choices. It ends with a code loop that removes a bad pattern with ast-grep and a documented Maya recipe.

## Prerequisites

- `python -m pytest plugin/cli/tests -q` passes from the repo root.
- `claude` 2.1.302 or later on `PATH` with working headless auth (the experiments and the live acceptance spend real money, a few dollars in total on haiku and sonnet).
- `gh` is installed (2.88.1 here); ast-grep is not, and TASK-155 installs it into a scratch virtual environment, never the system Python.

## Desired End State

- `compass loop new <name>` creates `.compass/loops/LOOP-NNN-name/` and refuses an existing folder. The loop's `index.md` appears in the root index under `## Loops`; `compass validate` reports no error for any file in the folder.
- `compass loop run LOOP-NNN` performs one iteration through the state machine below and leaves `state.json` in a resting state and one `run` row in `ledger.jsonl` carrying the sensor readings before and after, cost, turns, duration, the result subtype and the outcome.
- A run is refused before the actuator starts when the run's budget would push spend past the daily or lifetime budget the loop sums from its own ledger, or when unreviewed increments reach the WIP limit. The loop halts on an invalid sensor reading, on consecutive actuator failures, and on consecutive harmful runs.
- `compass test-checkpoint cycle` classifies each fix-loop cycle as helpful, neutral or harmful, and the build skill shows the human a harmful cycle before the next one.
- Four experiment documents under `.compass/research/pipeline/` each carry a verdict fixed before the run.

## Design

**The loop folder (D-01).** `.compass/loops/LOOP-NNN-name/` holds:

| File | Holds |
|---|---|
| `index.md` | the loop's document: `type: loop`, lifecycle `status`, `summary`, the end state (step 0) and one section per step describing the choice made |
| `loop.json` | the machine definition: sensor, set point, dampener, controller, actuator, caps, WIP limit, stop limits |
| `actuator.md` | the actuator's instructions |
| `golden/` | golden patterns: hand-written before/after pairs and anti-patterns |
| `feedback.md` | the human on the loop: durable guidance, version-controlled, loaded into every actuator run after the controller's output |
| `baseline.json` | the dampener's committed baseline: the sorted sensor items |
| `state.json` | the current state and counters |
| `ledger.jsonl` | append-only: one row per transition, run and review |

Optional sensor and controller scripts sit beside these. Only `index.md` is an artifact to the vault scanner; every other file in the folder is a loop part. Per-run scratch (the assembled prompt, the actuator's output) goes to `.compass/tmp/loops/LOOP-NNN/<run-id>/`, and the run lock to `.compass/tmp/loops/LOOP-NNN.lock`. A loop whose index `status` is not `active` refuses to run except with `--dry-run`.

**The state machine.** A pure `transition(state, event)` over one declared table; any other pair is refused. Resting states: `idle`, `throttled`, `paused`, `halted`, `done`. Working states: `sensing`, `gating`, `controlling`, `actuating`, `verifying`.

| From | Event | To |
|---|---|---|
| `idle`, `throttled` | `start` | `sensing` |
| `sensing` | `at-set-point` / `invalid-reading` / `off-set-point` | `done` / `halted` / `gating` |
| `gating` | `wip-full`, `daily-budget-spent` / `total-budget-spent` / `clear` | `throttled` / `halted` / `controlling` |
| `controlling` | `selected` / `nothing-selected` | `actuating` / `halted` |
| `actuating` | `finished` / `failed` / `failed-limit`, `controls-changed` | `verifying` / `idle` / `halted` |
| `verifying` | `helpful`, `neutral`, `harmful` / `harmful-limit`, `no-progress-limit` | `idle` / `halted` |
| `idle`, `throttled` | `pause` | `paused` |
| `paused`, `halted` | `resume` | `idle` |
| `done` | `reopen` | `idle` |
| any working state | `crash-recovered` | `idle` |

Every transition is written to `state.json` and appended to the ledger with its reason. A run that finds a working state on disk, with no live lock, records the earlier run as `crashed`, charged its full run budget, and recovers first. Reviews and dry runs are not transitions: a review is a ledger row, and a dry run works on state held in memory.

**Sensors.** The run sensor reads the actuator's result event (`--output-format json`): `total_cost_usd`, `num_turns`, `duration_ms`, `subtype`, `is_error`, and the input, output and cache token totals from `modelUsage`. On a budget stop it reads `total_cost_usd` and `modelUsage`, never `usage`, which is zeroed (finding 89). The domain sensor is the loop's own command, run from the project root. It prints JSON `{"valid": true, "value": <number>, "items": [<sorted identities>]}`; unparseable output or `valid: false` is an invalid reading that halts the loop, never "no findings" (finding 15). An item's identity stays the same under unrelated edits: a file and the matched text, never a line number. The set point is a `target` and a `direction` (`down` or `up`).

**Judging a change.** After the actuator, the domain sensor runs again on the same checkout the actuator changed. Helpful: the value moved toward the target and no item is new. Harmful: the value moved away, or any item is new (items compare as a multiset). Neutral: anything else. Defaults: halt after 3 consecutive actuator failures (12-factor factor 9, finding 53), after 2 consecutive harmful runs, and after 5 verified runs with no helpful one. Every counter starts again at a `resume`.

**Caps and budget.** Per run: `--max-turns`, `--max-budget-usd` and a wall-clock timeout that kills the process tree. Each iteration is a fresh session, never a resume, because a resumed session gets a fresh budget cap (finding 88). Across runs the loop sums `cost_usd` from its own ledger, since no product offers a per-day or per-loop cap (finding 112). When today's UTC spend plus the run budget would exceed `daily_budget_usd`, the run ends `throttled` and the next day's run proceeds; when the lifetime spend plus the run budget would exceed `total_budget_usd`, the loop halts for the human. A run with no result event counts as its full run budget.

**WIP and the human.** Every run that reached `verifying` leaves an increment, which awaits review until `compass loop review LOOP-NNN <run-id> accept|reject [--reason ...]` appends a review row. A reject reason is appended to `feedback.md`. The WIP count is the unreviewed increments; a `wip_command` in `loop.json` that prints an integer (for example a count of open pull requests carrying a label the loop puts on its own) replaces it.

**Controller and actuator.** Each run row records the item the controller selected. Controller `first` picks the first sorted item not held by an unreviewed increment; `command` runs the loop's own script, whose stdout is the control signal. The actuator prompt is `actuator.md`, then `## Golden patterns` (each `golden/*.md`), then `## Selected work (controller output)`, then `## Feedback` (`feedback.md`) (finding 31). It runs as `claude -p --output-format json --model M --max-turns N --max-budget-usd B --allowedTools T`. The prompt arrives on stdin, the environment adds `COMPASS_WORKER_SESSION=1` (the marker that stops Compass's own hooks from firing inside a headless session), and the binary resolves through `capture_worker._resolve_binary`, so `COMPASS_CLAUDE_BIN` stubs it in tests. A dsh binary is refused. The actuator is a top-level session, which the guard never judges (finding 120), so the runner hashes `loop.json`, `state.json`, `ledger.jsonl` and `baseline.json` before actuating and halts if any changed.

**Dampener.** `compass loop baseline` commits the sensor's sorted items to `baseline.json`. `compass loop check` prints items not in the baseline, and items fixed since. It exits 1 only with `--blocking`, so the check is advisory by default (finding 27), and the baseline shrinks only when `baseline` is re-run.

**Shared file.** `plugin/cli/maincli.py` changes only in TASK-150: the new `loop` entry, and `cycle` added to the `test-checkpoint` help line for TASK-152. `commands/loop.py` dispatches `run`, `check` and `baseline` to `looprunner`, and answers "not implemented yet" until TASK-151 lands.

## Not Doing

- No scheduler inside Compass; any scheduler calls `compass loop run`. The schedule step is Later.
- No automatic revert: a harmful increment is recorded and left for the human (the Data rule).
- No git operations in the runner; branching, committing and opening PRs belong to the actuator's instructions or the scheduled workflow.
- No telemetry intake (Sentry, PostHog); a controller script may call them.
- No PR-comment `/iterate` channel; `feedback.md` and `review` are the steering surfaces.
- `compass clone` keeps its own result parser.
