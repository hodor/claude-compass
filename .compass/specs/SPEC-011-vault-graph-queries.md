# The Vault's Graph Is Queryable by the Harness

## Problem

The vault is a graph that cannot be asked questions. Five edge types already exist - wikilinks, `depends_on`, folder/unit containment, tag hyperedges, and `decisions:` D-NN citations - but no mechanism can answer a multi-hop question over them: which artifacts does touching this spec ripple into; which lessons and decisions sit in this task's neighborhood; which plan implements the decisions this research influenced; what is orphaned, what is a hub. Agents that need these answers either cannot get them or reconstruct them by crawling the vault in agent tokens - the vault-health skill's orphan and backlink detection is documented as a full agent-token crawl, a direct violation of the harness-over-prompts principle for work that is purely mechanical graph traversal.

The cost lands on every ranked goal: navigation questions that should be one cheap query become either unanswered (accuracy risk when a planner misses a ripple) or expensive crawls (token cost, cache pollution).

## Who is affected

- The planner, which cannot ask "what does changing this spec impact" and so plans without the ripple map.
- The validator, which cannot walk decision lineage (spec ruling to plan task to implementation) as a query.
- The checkup and vault-health skills, which burn agent tokens crawling for orphans and backlinks the harness could compute.
- Any agent needing an artifact's neighborhood as context, which today loads whole documents instead of a bounded subgraph.

## Decisions (made by the human)

- **D-01:** Graph engineering in Compass means queries over the structure the vault already has, not a new store: markdown stays the source of truth, any graph artifact is derived and regenerated by the harness, and no external database, embedding model, or LLM extraction enters the vault path. (Direction set from [[RESEARCH-graph-engineering-for-compass]]; the extraction/resolution stages of the KG playbook are unnecessary because the vault is structured at authoring time.)
- **D-02:** The premise itself is not yet accepted: agents already query the vault with grep, and whether grep is genuinely insufficient for the needs this spec names is an open empirical question. The research/experiment phase must measure grep-based answers against the named query classes (multi-hop ripple, decision lineage, orphan detection) on this vault before any build; if grep plus existing CLI commands answer them correctly and cheaply, this spec is rejected rather than built. (Roger, 2026-07-26.)

## Desired Outcome

The harness can answer graph questions about the vault cheaply and deterministically: backlinks and orphans, impact-of-change traversal from any artifact, decision lineage across the pipeline, and a bounded neighborhood (k-hop subgraph) of any artifact serialized in a form agents can consume and cite. Skills that today crawl in agent tokens delegate to these queries.

## Needs (what a solution must satisfy)

- Multi-hop queries over the existing edge types (wikilinks, depends_on, containment, tags, decision citations) answered by the harness, off the agent token budget.
- Backlink and orphan analysis replaces the vault-health agent-token crawl.
- Impact-of-change traversal from a named artifact, bounded in depth, usable by the planner.
- Decision-lineage queries over D-NN citation edges, usable by the validator.
- A bounded neighborhood of a seed artifact serializable as context agents can cite, with the edges named.
- Graph health analytics (fragmentation, hubs, density) available to checkup-type skills.
- The graph representation is derived from the markdown on every vault write, never hand-maintained, and adds no new runtime dependencies.

## Hypothesis (falsifiable)

If the harness exposes graph queries over the vault's existing edges, then agent-token graph crawls disappear from the skills that do them, planners and validators consume ripple and lineage answers they previously could not ask for, and the cost per query is negligible against the agent-token crawl it replaces.

## Falsification criteria

- A graph question the needs list names still requires an agent-token crawl or stays unanswerable.
- The derived graph drifts from the markdown (stale answers) because regeneration is not tied to vault writes.
- Query cost or the derived artifact's size grows enough to threaten the hot-path or cache discipline.
- The mechanism requires a new external dependency, store, or service to function.

## Success criteria

- The named query classes (backlinks/orphans, impact traversal, decision lineage, k-hop neighborhood, health analytics) answer correctly on this vault, verified against hand-checked expected results.
- vault-health's orphan/backlink step invokes the harness query instead of crawling.
- Regeneration rides the existing write-hook path and stays current without agent involvement.
- Zero new runtime dependencies; markdown remains the only source of truth.

## Non-Goals

- Choosing the storage format, query syntax, or traversal algorithms - research/ADR/plan territory. (The completed research recommends a derived graph file built by sync plus a query command; prior art: the KG playbook's k-hop serialization and diagnostics.)
- LLM entity extraction, embeddings, semantic retrieval, AST code graphs, or external graph databases - all explicitly deferred with the same triggers as the RAG decision ([[RESEARCH-rag-fit-for-large-vaults]]).
- Changing what edges authors write; this consumes existing conventions.

## Open questions (for research/ADR, after approval)

- Which consumers get wired first (vault-health replacement is the cheapest proof; planner impact and validator lineage are the accuracy wins).
- The k-hop serialization format agents cite (the playbook's triple form vs a markdown rendering).
- Whether tag hyperedges join the first version or wait (they widen neighborhoods fast).
- How graph health analytics fold into checkup vs a dedicated report.
