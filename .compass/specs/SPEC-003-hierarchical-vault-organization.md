# Hierarchical Vault Organization with Faceted Tags

## Problem

The current flat vault layout (`SPEC-NNN-name.md` all at top level) does not scale. As a project accumulates specs, three failure modes appear:

1. **Hot path blows up.** Every spec must appear in `index.md`. With 100+ specs, the index alone consumes thousands of context tokens on every agent turn.
2. **Multi-perspective specs have no good home.** A "master material" spec is both a `#rendering` concern and a `#tile-editor` concern. Strict folders force one parent, so the spec gets buried where one search angle can't find it.
3. **Large feature specs become mid-context blobs.** A 5,000-line spec for "tile editor" sits in the middle of the agent's context, where the documented "lost in the middle" U-curve costs 20-30 points of retrieval accuracy across all frontier LLMs.

These are not theoretical. The same failure modes are documented in MemGPT (capacity collapse, memory blindness), Ranganathan (1933, faceted classification developed specifically to solve the multi-parent problem), Denning (working set thrashing as a phase transition), and Liu et al. TACL 2024 (lost-in-the-middle).

## Desired Outcome

A vault layout that scales to hundreds of specs without inflating the agent's hot path, where any spec can be reached from any reasonable angle in two reads or fewer, and where adding a new perspective on an existing spec does not require restructuring the tree.

## Hypothesis (falsifiable)

A hierarchical vault with facet tags, RAPTOR-style branch summaries, and hot-path admission control will reduce per-task vault-read token count by at least 30% versus a flat vault, on tasks that touch two or more specs, with no loss in task completion rate.

## Falsification criteria

The design is wrong if any of the following hold after implementation:
- Per-task vault-read tokens are within plus-or-minus 10% of the flat vault on five or more representative tasks.
- The root index exceeds 5,000 tokens with 50+ specs in the vault.
- The agent crawls directories to satisfy a multi-tag query instead of using the tag index.
- A spec migrated from flat to hierarchical breaks any inbound wikilink.

## Success criteria

- Hot path stays under 5,000 tokens with 50 specs and 10 lessons.
- Single-spec navigation costs at most two reads (root index plus the leaf).
- Multi-perspective retrieval uses the tag index, not folder crawl.
- Flat-to-hierarchical migration preserves every existing wikilink.
- Branch summaries score 4 out of 5 on a blinded LLM rubric for "does this summary represent its children faithfully."

## Constraints

- Must be backward-compatible with existing flat specs. Existing `SPEC-001-*.md` and `SPEC-002-*.md` continue to work without migration.
- Migration must be a tool, not a manual rewrite.
- The agent must never need to crawl the directory tree to find a spec. Every navigation is satisfied by one of: root index, a folder index, or the tag index.

## Non-Goals

- Solving cross-project taxonomy. Each Compass vault is independent.
- Building a global controlled vocabulary. Tags are folksonomy with periodic consolidation.
- Predictive prefetching of specs. Promotion is reactive (query-driven), not predictive.
- Migrating from this scheme to some future scheme. Out of scope for this spec.

## Risks

- **Tag sprawl.** Folksonomy invites synonyms and typos. Mitigation: `/compass:consolidate` runs a tag-vocabulary pass and proposes merges.
- **Branch summary drift.** Folder `index.md` files can fall out of sync with their children. Mitigation: every child write triggers a "summary may be stale" flag in `index-sync`; periodic refresh via `/compass:consolidate`.
- **Admission-control thrashing.** Too aggressive and the agent runs out of hot path; too lax and it forgets which specs exist. Mitigation: ship with conservative defaults, tune from real usage.
- **The 30% read reduction claim might not hold.** This is a real falsification target. If empirical measurement shows hierarchy adds overhead without benefit, the design is wrong and we revert to flat with stricter index hygiene.

## Open Questions

All resolved in [[ADR-004-hierarchical-specs-with-facets]]. Summary:

- Branch summaries: auto-generated by an LLM pass at write time, human-approval gate.
- Tag vocabulary: folksonomy with periodic consolidation, not controlled.
- Admission-control signal: working-set heuristic (specs touched in the last N turns), with token-count as a hard ceiling.
- Lessons catalog in hot path: stays as a single file in the hot path; tags on specs do not duplicate lesson tags.
