# The Vault's Graph Is Queryable by the Harness

## Problem

Three questions over the vault's link structure cost more than they should or come out wrong.

**Orphan detection is a shipping agent-token crawl.** vault-health and checkup both carry an orphan step; vault-health's instructs the agent to read `index.md` and every vault file's wikilinks in context, a whole-vault crawl on a recurring cadence (before handoffs, periodic maintenance) in every Compass install. The correct orphan definition is subtle: `compass sync` links every artifact into `index.md`, so a naive "zero inbound edges" query returns nothing, and the real question is zero inbound besides the index catalog row. An agent re-deriving that rule ad hoc gets it wrong.

**Hub ranking has no primitive, and a recorded defect needs one.** `compass unit-check`'s candidate detection is degraded by SPEC-001's dominance as a hub (17 inbound `depends_on` edges); the recorded fix is a heuristic that requires inbound-degree ranking it cannot compute today. Hand-computing that ranking in [[RESEARCH-grep-vs-graph-experiment]] required a 20.7KB dump of `depends_on:` lines hand-tallied with no verification step.

**Impact-of-change traversal comes out wrong even when done carefully.** "What does touching this spec ripple into" took 5 grep calls across 2 rounds plus manual judgment separating structural edges (`depends_on:`, real wikilinks) from narrative prose mentions of a document's name, and the hand-computed answer was still wrong: the experiment's 2-hop set for SPEC-003 admitted two documents that only mention a hop-1 node in prose and omitted two that genuinely depend on one. The miscount the experiment predicted for an agent under working pressure happened in the experiment's own controlled conditions, and the planner consumes this answer when deciding what a change affects.

## Who is affected

- vault-health and checkup, whose orphan steps burn agent tokens crawling the vault.
- `compass unit-check`, whose promotion heuristic is degraded by hub inflation it cannot measure.
- The planner, which answers "what does this change affect" by manual judgment shown to miscount in both directions. No planner step consumes a ripple answer today, so the consuming step is part of this spec's scope, not an assumption.

## Decisions (made by the human)

- **D-01:** Graph engineering in Compass means queries over the structure the vault already has, not a new store: markdown stays the source of truth, any graph artifact is derived and regenerated by the harness, and no external database, embedding model, or LLM extraction enters the vault path. (Direction set from [[RESEARCH-graph-engineering-for-compass]].)
- **D-02:** The spec's premise had to survive a grep-vs-graph experiment before any build; blanket sufficiency of grep would have rejected it.
- **D-03:** First narrowing on the experiment's verdicts: single-artifact backlinks and decision lineage dropped as already covered; scope centered on the classes grep handles worst.
- **D-04:** Scope corrected after a three-lens review (spec hygiene, systems, adversarial product), which scoped by consumers rather than by grep difficulty: orphan detection promoted to core as the only class with shipped recurring consumers; hub ranking retained with `unit-check`'s inbound-degree defect as its consumer; impact traversal retained on the accuracy evidence that even the experiment's careful hand answer miscounted in both directions, with the consuming planner step in scope; fragmentation, density, and the k-hop rider cut.

## Desired Outcome

The harness answers orphan detection, hub ranking, and bounded impact-of-change traversal deterministically and off the agent token budget. The skills and commands that need those answers consume them: vault-health and checkup stop crawling, unit-check's heuristic gets its degree data, and the planner gains the step that reads the ripple answer.

## Needs (what a solution must satisfy)

- Orphan detection - artifacts with no inbound edge other than the `index.md` catalog row - computed by the harness, replacing the whole-vault crawl in vault-health and the orphan check in checkup.
- Inbound-degree hub ranking over structural edges, consumable by `unit-check`'s promotion heuristic.
- Impact-of-change traversal from a named artifact over structural edges (`depends_on`, wikilinks, containment), bounded in depth, distinguishing structural edges from prose mentions.
- A planner step that consumes the traversal answer ships with the query; the query has a consumer from day one.
- Answers name the specific edges that produced them, so a consumer can audit the traversal rather than trust the total.
- Answers are always consistent with the markdown at the moment they are given, or the mechanism detects and reports that it is behind. Deletions, renames, and CLI-driven moves do not pass through the write hook, so staleness must be detectable, not merely assumed away.
- Answers are off the agent token budget, per [[SPEC-004-mechanical-work-off-the-agent-budget]]. Nothing hand-maintained; no new runtime dependencies.

## Hypothesis (falsifiable)

If the harness answers these three query classes, then the orphan crawls disappear from vault-health and checkup, unit-check's hub defect becomes fixable, planners consume ripple answers that manual judgment got wrong in both directions, and the cost per query is negligible against what it replaces.

## Falsification criteria

- A core-scope question still requires an agent-token crawl or stays unanswerable.
- A query returns an answer that disagrees with the markdown (stale or missing edges).
- The harness answer still needs manual structural-vs-prose disambiguation, making it no more trustworthy than the crawl it replaces.
- Query cost or any derived artifact's size grows enough to threaten the hot-path or cache discipline.
- The mechanism requires a new external dependency, store, or service to function.

## Success criteria

- Answers verified against ground truth recomputed at validation time, never a frozen set. The stable anchor is hub dominance: [[SPEC-001-compass-vision-and-architecture]] first at 17 inbound `depends_on` edges, ADR-005 second at 11 (measured 2026-08-05, 68 documents). The impact-traversal check recomputes the SPEC-003 closure independently; the set recorded in [[RESEARCH-grep-vs-graph-experiment]] is wrong in both directions and is retained there only as an illustration of the hand-tally failure mode.
- vault-health's and checkup's orphan steps invoke the harness query instead of crawling.
- The planner step consuming the traversal answer ships and is exercised on at least one real plan.
- Zero new runtime dependencies; markdown remains the only source of truth.

## Non-Goals

- Single-artifact backlink lookup (one grep call, low noise) and decision-lineage queries (`compass decisions` / `compass coverage` are CLI-native) - measured as already solved in [[RESEARCH-grep-vs-graph-experiment]]. This spec claims neither.
- Fragmentation and density metrics. `compass sync` links every artifact into `index.md`, so the vault is connected by construction; these would report on sync's health, which `compass validate` already covers.
- k-hop neighborhood serialization. Nothing consumes it; revisit only with a named consumer.
- LLM entity extraction, embeddings, semantic retrieval, AST code graphs, or external graph databases - all deferred with the same triggers as the RAG decision ([[RESEARCH-rag-fit-for-large-vaults]]).
- Lesson retrieval - [[SPEC-012-learning-loop]] pillar 2 owns it, and lessons carry no artifact-graph edges.
- Changing what edges authors write; this consumes existing conventions.

## Open questions (for research/ADR, after approval)

- Substrate: a derived graph file built by sync, or on-demand traversal at query time. (Genuinely open; the staleness-detection need constrains both options without choosing.)
- Edge semantics: does a wikilink appearing in narrative prose count as an impact edge, and is the answer the same for `depends_on` and wikilinks?
- Whether `doc/D-NN` decision-citation edges join the traversal edge set. (The lineage query is out of scope; the edge type is not automatically.)
- The shape of the planner's consuming step: what it reads, where the answer lands in the plan.
