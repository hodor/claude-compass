# Compass Development

You are working in the Compass plugin repo. This project has **two roles** that share the same git repo and you must be conscious of which role you are in for any given edit:

| Role | Where you edit | Who consumes your work |
|---|---|---|
| **Plugin developer** | `plugin/` (skills, agents, hooks, templates that ship to users) | Anyone who installs Compass |
| **Plugin user, dogfooding** | `.compass/` (specs, plans, ADRs, lessons, research about how this very plugin should evolve) | The next Compass-developing session |

If you change `plugin/skills/foo/SKILL.md`, you are shipping a behavior change to every Compass user. If you write `.compass/specs/SPEC-005-foo.md`, you are recording a decision about how this plugin should be designed. The two often pair: a spec in `.compass/` decides what to build; a change in `plugin/` builds it.

**Never confuse these directories.** Editing a file in `.compass/` does NOT change the plugin behavior. Editing a file in `plugin/` does NOT update the dev decisions.

## Repo layout

| Path | Distributed to users? | Purpose |
|---|---|---|
| `plugin/` | Yes - this is the install target | Agents, skills, rules, hooks. Everything `/compass:setup` copies into a project. |
| `.compass/` | No | Compass's own dogfood vault. Where this plugin's design lives. |
| `.claude/` | Gitignored | Local install of plugin templates into this project, generated by setup. Lets `/compass:*` commands work in THIS repo without `--plugin-dir`. |
| `bench/` | No | Benchmark harness for measuring Compass vs plain Claude Code. Not part of any user install. |
| `README.md`, `CLAUDE.md` | No | Repo-level docs. |

`.claude/` is the **local install** that makes `/compass:*` commands available when running Claude Code inside this repo. It is rebuilt from `plugin/` by `/compass:update` whenever the plugin changes. If you modify a skill in `plugin/skills/foo/SKILL.md`, copy it into `.claude/skills/foo/SKILL.md` for the change to take effect in the current session, OR run `/compass:update`.

## Session start protocol

Every session MUST begin by reading the hot path:

1. `.compass/index.md` - master map (tree, pointers, never spec bodies). Hard cap 5,000 tokens per [[SPEC-003-hierarchical-vault-organization]].
2. `.compass/active.md` - current tasks, blockers, next up.
3. `.compass/meta/lessons-catalog.yaml` - scan for relevant lessons.

Place these at the START of your reasoning, never in the middle of a long prompt. Lost-in-the-middle costs 20-30 points of accuracy across frontier models (ADR-004).

Use `.compass/meta/tag-index.yaml` (cold-tier) for multi-perspective queries; don't crawl folders.

## Methodology

Read `plugin/skills/methodology/SKILL.md` for the full workflow. Key points:

- **Pipeline:** Vision → Spec → Research → Plan → Build → Validate
- **Human involvement gradient:** Specs (human decides) → Research (AI executes, human reviews) → Plans (AI proposes, human approves) → Build (AI executes autonomously)
- **Testing mandate:** Every agent that writes code must write tests and run the full suite
- **Lessons:** Captured retrospectively at phase boundaries (not in-flight). See ADR-002.
- **Numbering:** JIT max+1 from filesystem, local per folder. NO counter file. See ADR-003.
- **Hierarchical specs:** Folders for complex specs, faceted tags for multi-perspective. See ADR-004.

## Slash commands

After setup, `/compass:*` commands are available in this repo. Categories:

**Capture and design:** `/compass:vision`, `/compass:spec`, `/compass:specs`, `/compass:research`, `/compass:research-codebase`, `/compass:research-papers`, `/compass:papers`, `/compass:plan`

**Execute:** `/compass:build`, `/compass:autopilot`, `/compass:validate`, `/compass:diagnose`

**Maintain:** `/compass:checkup`, `/compass:vault-health`, `/compass:consolidate`, `/compass:annotate`

**Migrate:** `/compass:promote-spec`, `/compass:taxonomize`

**Session continuity:** `/compass:handoff`, `/compass:learned`, `/compass:retroactive`

**Setup & update:** `/compass:setup` (new / migrate) for first-time setup; `/compass:update` to refresh an existing install from GitHub.

## North star goals (SPEC-001)

Every design decision serves at least one of these four, ranked:

1. **Accuracy** - outputs are correct, claims verified.
2. **Perfect memory** - vault is single source of truth across sessions.
3. **Almost zero cache misses** - bounded hot path, hierarchical access, tag-index for multi-parent.
4. **Low token usage** - mechanical work in scripts and hooks, never in agent tokens.

When proposing a `plugin/` change, ask which goal it serves.

## Commit rules

- Always `git add <specific-file>` for vault files; never `-A` or `.`
- Never commit `.compass/tmp/` (gitignored)
- Never commit `bench/external/`, `bench/runs/*/workspace/`, `bench/runs/*/eval_*/` (gitignored)
- Never commit `.claude/` (gitignored - it is a generated local install)
- Commit messages: imperative mood, explain why not what
- No `Co-Authored-By` lines
- Only commit when explicitly instructed

## Vault structure

```
.compass/
├── index.md                  - HOT: master map (tree-rendered, pointers only, ≤5K tokens)
├── active.md                 - HOT: current tasks
├── backlog.md                - cold: future tasks
├── meta/
│   ├── lessons-catalog.yaml  - lesson tag index (loaded with hot path)
│   ├── tag-index.yaml        - facet index (loaded on demand for multi-tag queries)
│   └── plugin.yaml           - plugin source path + installed version (for /compass:update)
├── specs/                    - specifications (flat OR folders for complex specs)
├── research/                 - research findings with confidence levels
├── plans/                    - implementation plans (mirror spec hierarchy)
├── decisions/                - ADRs
├── lessons/                  - lessons learned (5-line cap per body)
├── handoffs/                 - session continuity snapshots
├── prs/                      - PR descriptions
└── archive/                  - completed/retired documents
```

A spec earns its own folder when its body exceeds ~2K tokens OR it has 3+ sub-concerns. Folder `index.md` is the parent spec at that level.

## When in doubt

Read the most recent handoff in `.compass/handoffs/` first. It tells you what state we are in and what is next.
